# Write winuse in Go

winuse is written in Go, although most Windows accessibility tools use Rust, C# or Python. We chose Go for fast builds and to match use-browser (a single dependency-free Go binary installed by a one-line script). Go has no maintained UI Automation library, so we call the COM interfaces directly through `syscall.SyscallN` vtables with no cgo, using y3owk1n/neru (MIT) as the reference implementation and zzl/go-win32api (MPL-2.0, generated from Microsoft's win32metadata) for interface layouts.

## Consequences

- All COM work runs on one OS-locked goroutine that called `CoInitializeEx`; other code reaches it through a channel. The Esc keyboard hook likewise needs its own locked thread with a message loop. *(Amended by [ADR 0009](0009-com-homes.md): one COM home per technology — the UIA MTA thread, the Windows.Graphics.Capture MTA thread, and a throwaway STA around ShellExecuteEx — with COM state never leaving its home.)*
- COM reference counting is manual (no RAII), so leaks and double releases are the main bug class to test for.
- Screenshots follow Codex and use Windows.Graphics.Capture (WinRT), which has no Go bindings and must be hand-written alongside Direct3D interop; this is the riskiest part of the Go choice. GDI capture (screen region, then `PrintWindow`) is kept as the fallback when it fails. If WinRT work grows beyond capture, revisit this decision in favour of Rust's official `windows` crate.
- Named-pipe IPC to the background helper uses Microsoft/go-winio (MIT).
